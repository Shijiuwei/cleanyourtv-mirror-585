Samsung, LG, Roku or another non-Android TV? CleanYourTV can't run there, but you can still turn off the tracking, step by step with your remote: cleanyour.tv/not-android

The viral tweet: x.com/gathint/status/2111379569030939102

On 17 October 2026 I posted a before and after of my parents' TV, cleaned up by Claude Code over Wi-Fi. It reached 7.4M views, people started doing the same to their own TVs, and their replies turned into the lists here: 170+ TV models from 200+ contributors in four days. The repo was called tv-vibehack until the 19th; old links work.

Themes, switches and add-ons: cleanyour.tv/addons

Official links: the website is cleanyour.tv and the code, launcher and tools live only in this repo. Other domains using the name, such as cleanyourtv.com, are not run by this project (#1004).

How it works

Android TVs have the same debug bridge as Android phones. Switch on USB debugging in the TV's developer options, allow your computer once, and the rest is standard Android tooling:

StepWhat happens
Back upThe list of installed packages and settings.
DisableThe manufacturer's telemetry, ad services, content rows and preloaded junk, with pm disable-user. Nothing is uninstalled, so a restore script can undo every step.
InstallA small native launcher, made the default home screen.

No root, no cable, nothing uninstalled, and a one-line restore if you change your mind.

The bloat differs by brand, so the prompt has your coding assistant discover it on your TV and ask before touching anything you might use.

Quick start

You haveDo this
A computerUse the prompt with a coding assistant: the three steps below.
A computer, no coding assistantRun the three steps yourself: the commands are in Doing it by hand.
Only an Android phoneUse the community-built Clean Your TV app by @udhaykumarbala: connect, analyse, clean, in about five minutes. No laptop, no coding agent.

The three steps below are written for a coding assistant: the computer needs to be on the same Wi-Fi as the TV, with a shell on it. Without an assistant, Doing it by hand is the same job, run by you.

Any of these work: Claude Code (on 0G Private Computer or an Anthropic plan), Codex, Gemini CLI or Antigravity CLI.

WhereWhat to do
1. On the TVSettings → Device Preferences → About → press OK on Build seven times → back → Developer options → USB debugging on. If you see a Network or ADB debugging toggle, turn that on too. Keep the TV on.
2. On your computerClone the repo and open that folder in your assistant (git clone https://github.com/Gathin23/cleanyourtv), then paste PROMPT.md and fill in your TV model.
3. Follow alongAccept "Allow USB debugging?" on the TV, then answer the checklist: which apps you use, the dock size and app order, whether to keep the voice assistant, Chromecast and updates.

Cloning matters: the assistant reuses this repo's tools/disable.sh and launcher/build-and-install.sh instead of writing its own, and that is where the backup, the Home guard and the restore record live.

The assistant backs up, debloats, builds and installs the launcher, and checks each step with screenshots pulled from the TV. With this repo as context it takes about fifteen minutes.

Supported TVs

Anything running Android TV or Google TV.

PlatformWhat works
Android TV, Google TVThe debloat and the launcher.
Fire TVThe debloat half only, since Fire OS will not hand Home to a third-party launcher. And on the 2015 Fire TV Box (Fire OS 5) even that half fails: every pm route is refused.
A few China-market TCL setsThey refuse to install any launcher at all; their lists say so in the header.
Samsung (Tizen), LG (webOS), Roku, Vizio, Hisense VIDAANot supported (no ADB). Turn off the tracking instead: cleanyour.tv/not-android. See SHOWCASE.md for four webOS ports, and docs/devices/samsung-tizen.md for what a 2021 Samsung set answers over Wi-Fi (no ADB, so no pm disable-user) if you are weighing a Tizen port.

Doing it by hand

Everything the assistant does, you can run yourself. The tools need Python 3 and nothing else. tools/tv.py talks to network ADB on port 5555. If that port stays closed and the TV offers Wireless debugging with a pairing code (the Chromecast with Google TV and the Google TV Streamer do), pair it once with the stock adb and run adb tcpip 5555 first, as Troubleshooting describes.

python3 -m venv tools/venv && tools/venv/bin/pip install -r tools/requirements.txt
export TV_HOST=192.168.1.50                                   # your TV's IP address

tools/venv/bin/python -I tools/tv.py --probe                 # model, Android version, firmware
tools/venv/bin/python -I tools/tv.py 'pm list packages'      # one shell command on the TV
tools/disable.sh examples/xiaomi-mi-tv-4a/debloat.txt        # apply a debloat list
tools/restore.sh examples/xiaomi-mi-tv-4a/debloat.txt        # undo it, stock launcher back
tools/venv/bin/python -I tools/check.py examples/xiaomi-mi-tv-4a/debloat.txt   # what a firmware update undid
TV_HOST=192.168.1.50 launcher/build-and-install.sh           # build the launcher and make it Home
tools/theme.sh themes/aurora                                 # push a theme; --reset removes it

The scripts never leave the TV without a Home app: they only disable a stock launcher they recognise, and skip the Home app in a list until another launcher answers HOME. Details below.

Windows (PowerShell)

Every script has a PowerShell twin next to it. On Windows with Android Studio installed nothing else is needed:

python -m venv tools\venv; tools\venv\Scripts\python.exe -m pip install -r tools\requirements.txt
powershell -ExecutionPolicy Bypass -File launcher\build-and-install.ps1 -TvHost 192.168.1.50
powershell -ExecutionPolicy Bypass -File tools\disable.ps1 -TvHost 192.168.1.50 examples\xiaomi-mi-tv-4a\debloat.txt
How the scripts protect Home

The install scripts ask the TV which launcher owns Home and only disable one they recognise, the four in KNOWN_STOCK_LAUNCHERS: com.google.android.tvlauncher, com.google.android.apps.tv.launcherx, com.google.android.leanbacklauncher and Xiaomi's com.mitv.tvhome (PatchWall). Pass STOCK_LAUNCHER=<package> (-StockLauncher) to override, or none to leave it alone.

tools/disable.sh (disable.ps1) applies the same rule before it disables anything: if the list contains the app that owns Home and no other app on the TV answers HOME, it skips that entry, says why, and disables the rest of the list. The setup wizard, the settings apps, a vendor FallbackHome and factory-test apps (Xiaomi's com.duokan.factorytest) answer HOME too and don't count. So a list applied before the launcher handover cannot leave the TV with nothing to start. Run the same list again once launcher/build-and-install.sh has made the new launcher Home and the entry is applied; FORCE_HOME=1 ($env:FORCE_HOME) disables it anyway.

Where your lists can live

Debloat list paths passed to disable.sh and restore.sh are relative to the directory you run from, so your own lists can live outside the repository. Absolute paths also work.

The microphone, and what can be said about it

"Which of these packages is listening?" has no honest one-line answer, and a permission scan makes it worse: on many sets most packages run as android.uid.system, so fifty of them show RECORD_AUDIO: granted=true and none of them record anything. On others the microphone is in the remote, not the panel, and a package with no audio permission at all still sees everything on screen — ACR clients such as tv.inscape.tvclient.inscapeacr identify content from the picture and need only INTERNET.

tools/privacy.py reports what the TV actually says instead of guessing: TV_HOST=192.168.1.50 tools/venv/bin/python -I tools/privacy.py prints voice, ACR and telemetry candidates in three groups, each with its evidence — named by the firmware's own voice_interaction_service, a known component from examples/, or nothing but a matching name — plus whether the package declares RECORD_AUDIO, whether it shares the system UID, and whether the returned AppOps history contains microphone access. A configured mode or a rejected attempt alone is not evidence of access.

--write privacy.txt turns the identified candidates into a normal debloat list, so applying it and undoing it are the commands you already use (tools/disable.sh, tools/restore.sh). Packages that only matched by name stay out unless you pass --include-low; they are the ones to check with dumpsys package <name> first.

What the audit cannot do is prove intent. appops shows an op was touched, not what happened to the stream afterwards, and no scan of package names proves a TV is or is not recording. Disabling an assistant is a trade you make with a specific loss (the remote's mic button, voice search inside apps), which is why the report names that loss per package instead of calling it a win.

The launcher

A small native home screen for Android TV: about 532 KB, plain Java, built for TVs with 1 GB of RAM. No blur, no video, no network permission, no background services.

The TV needs Android 8.0 (API 26) or newer: minSdk is a compile-time floor in launcher/app/build.gradle, and the install script asks the TV for ro.build.version.sdk before it builds, so an older set is told both numbers instead of failing at pm install (see Troubleshooting for what is left on such a set).

What the record holds, and what happens without one

Before tools/disable.sh changes anything it writes down what the TV looked like: for every package in the list whether it was enabled, already disabled or not installed, which component owned Home, and the three animation scales. That record lives in ~/.cleanyourtv/, one file per TV and list, and a second run of the same list keeps the first record instead of saving the cleaned-up state over it. If you added packages to the list since, that run adds them to the record before disabling them, and a listed package that was not installed then but is installed and enabled now is recorded as enabled. check.py --fix does the same before it disables anything.

Keep the list you applied. The restore script replays the record, so a package you had disabled yourself stays disabled and Home goes back to the component that owned it:

The stock launcher argument is only a fallback: with a record, the launcher that actually owned Home is the one that gets it back, and the argument is used only when nothing answered HOME at the time or this project's launcher owned it. The stock launcher is enabled again either way, unless it was already disabled when the record was taken. Without a record (an older run, or a record you deleted) the script says so and falls back to enabling the whole list and resetting the scales to 1.0, which is what it used to do.

It leaves the new launcher installed (remove it from the TV's Settings → Apps if you want it gone) and does not know about packages you disabled outside the list. To switch back later, run the install script again; it works out which launcher to disable even when Home has fallen back to Android's chooser. If the TV is unreachable, its own Settings → Apps page can re-enable packages too.

After a firmware update

An update installs over the cleaned-up system: the listed packages come back, Home goes to the stock launcher, and new preloads appear that no list mentions. Nothing else here notices, so compare the TV with the list you applied.

The check and --fix reach the TV over network ADB. If you closed ADB as Isn't ADB access a security hole? describes, open it again first: USB debugging, and Network/ADB debugging if the TV has it, back on as in Quick start step 1. On a TV whose port 5555 only opens through Wireless debugging, switch that on as well, pair it again with the stock adb and run adb tcpip 5555, as in Doing it by hand. Closing revoked this computer's authorisation, so accept "Allow USB debugging?" on the TV when the check connects. While ADB is closed the check can only report "could not reach the TV", even with the TV on and TV_HOST right. Close ADB the same way once you are done. With it open:

TV_HOST=192.168.1.50 tools/venv/bin/python -I tools/check.py examples/<your tv>/debloat.txt

It exits with 0 when the TV still matches the list, 1 when something drifted, and 2 when it could not check at all: the TV did not answer, nobody accepted the "Allow USB debugging?" prompt in time, the list path is not there, the list disables Android's core packages, or, under --fix, the recovery record for this TV and list cannot be read or updated (nothing is changed on the TV then). Only 1 is drift, so a job that mails on 1 alone stays quiet while the check never ran; mail on anything but 0, or on 2 as well, and a weekly job on a home server or a Pi is enough to hear about it:

0 9 * * 1 cd ~/cleanyourtv && TV_HOST=192.168.1.50 tools/venv/bin/python -I tools/check.py examples/<your tv>/debloat.txt

TV_HOST is read before any of that: a run that leaves it unset stops in tools/tv.py with its own message and also exits 1, so set it in the job line, as above, where cron does not inherit it from your shell.

The job only gets an answer from a TV that keeps network ADB listening between runs and has accepted "Allow USB debugging?" for the computer that runs it with "Always allow from this computer" ticked: without the tick the TV asks again at every run, and with nobody there to accept, the run exits 2. A port left listening is the one Isn't ADB access a security hole? says to close, since anything on the network can reach it. With ADB closed as described there, every run exits 2: run the check by hand after an update instead, with ADB opened again as above.

--fix reapplies the list to what drifted: it switches Home to the launcher the list does not disable (pass a package as the second argument if you run a fork), then disables the listed packages that came back, and reads the TV back to confirm both. It never writes a recovery record of its own, because only the first run's record holds the state from before cleanup. When there is one, --fix first adds to it what a second tools/disable.sh run would (names the list gained, and a package that was not installed then and is installed and enabled now), so tools/restore.sh still returns the TV to stock afterwards. Home is fixed first; if no launcher is left to take it, --fix changes nothing and says so.

It runs the same safety checks as tools/disable.sh before it disables anything, since an update is the moment they matter again: it leaves setupwraith on while the saved Wi-Fi network belongs to it (FORCE_SETUPWRAITH=1 on Ethernet), leaves the packages under the HDMI/AV inputs on (TVINPUT_ALLOW=1 if you really want them off), leaves on the apps the TV opens its inputs and Settings with (HANDLERS_ALLOW=1), and never takes Home to a vendor FallbackHome or a factory-test app. Each package it leaves on comes with the reason and exits 1, because the TV is not back to the list until you deal with that one by hand.

With stock_home_redirect the stock launcher can stay Home on purpose: the list leaves it out, the install script ran with STOCK_LAUNCHER=none, Android keeps it as Home, and HomeKeyService sends its home screen on to this launcher. On the Chromecast with Google TV 4K that setup matches the folder's debloat-keep-cast.txt, not its debloat.txt, which disables setupwraith and the screensaver pair the redirect setup keeps. On the Acer AR55AR2851UDPRO it is the folder's debloat.txt. Check those lists with the stock launcher as the second argument. Without it the check expects com.gathin.tvhome on Home, so every run reports Home as drift, and --fix tries to move Home to it, which those TVs do not keep:

TV_HOST=192.168.1.50 tools/venv/bin/python -I tools/check.py examples/google-chromecast-gtv-4k/debloat-keep-cast.txt com.google.android.apps.tv.launcherx
TV_HOST=192.168.1.50 tools/venv/bin/python -I tools/check.py examples/acer-ar55ar2851udpro/debloat.txt com.google.android.tvlauncher

Leave the argument out where the stock launcher is meant to be off, disabled by the list or by the install script: the Chromecast's debloat.txt, where the install script disables launcherx, and the XGIMI projectors, where the redirect only covers for firmware that turns it back on. There the stock launcher on Home is drift, and naming it as the second argument would hide that drift.

Lists that also disable the updater get no updates at all. To install one, re-enable the updater on the TV, let it update, run check.py --fix, and disable the updater again.

On Windows the same command is tools\venv\Scripts\python.exe -I tools\check.py <list>.

When something goes wrong

The full list of things that bit us is in docs/TROUBLESHOOTING.md. The three that matter most:

  • 🍎 macOS blocks adb connect ("No route to host") under Local Network privacy. tools/tv.py avoids the binary.
  • ⚠️ Disable the stock launcher only after the new one is installed and running, or Home lands on a factory test app. The install script orders this for you.
  • 🔁 On Google TV the setup wizard (com.google.android.tungsten.setupwraith) can take Home and crash-loop the system after the stock launcher is disabled. Disable it too, and list it in your debloat.txt so restore brings it back. But check dumpsys wifi | grep -o 'cname=[^ ]*' first: if the Wi-Fi network was saved during setup it belongs to setupwraith, and disabling it deletes the network (re-join it in Settings first; tools/disable.sh skips setupwraith until you do). On Google's own Chromecast and on the Google TV Streamer it also costs phone casting, see Troubleshooting. Stuck already? tools/tv.py 'pm enable --user 0 com.google.android.apps.tv.launcherx'.

Questions people ask

I don't code and don't have a laptop. Can I still do this?

Yes. @udhaykumarbala built a free, open-source phone app for Android that does the same cleanup over Wi-Fi: it connects to the TV, shows a plan first, saves a restore point, and only switches apps off, so everything can be put back. It's community-built.

Is this safe? Can it brick the TV?

Nothing is flashed, rooted or deleted; packages are disabled in the user profile. The risk is disabling something the TV leans on, which is why lists are applied in small batches with a restore script ready. The TV's own Settings → Apps page can re-enable packages even without the tools.

If the TV no longer starts far enough for that, or for ADB, a factory reset from its recovery menu is usually the way back (#1578): everything these tools change lives in the user data the reset wipes, so every disabled app comes back and the new launcher is gone, along with your own apps and accounts. A TV that still restarts in a loop after the reset points to the hardware rather than the debloat (#1592); Troubleshooting has the cases seen so far.

What about firmware updates?

The updater is left on in most lists, so firmware updates arrive as usual. Some lists disable the TV's own updater, and on those a firmware update arrives only when you re-enable it. When one does land it installs over the cleaned-up system, so a package comes back and you re-run the script: see After a firmware update.

Won't the apps break?

Streaming apps still update through the Play Store, which is left alone. The launcher just lists what is installed and launches it with intents that have been stable for a decade.

Can I do this for someone in another home?

Yes, over a private Tailscale link instead of the same Wi-Fi: either Tailscale on their TV, shared with you, or a computer or Apple TV at their home routing to it. Never by opening the ADB port on their router. Step by step in docs/REMOTE.md.

Isn't ADB access a security hole?

It is one explicit "allow this computer" tap on the TV, the same as developing an Android app. Network ADB is plaintext on port 5555, and on firmware with ro.adb.secure=0 any device on the LAN gets a shell, so close it when you are done:

  1. On the TV: Developer options → turn USB debugging, Network/ADB debugging and Wireless debugging off, whichever the TV has, and revoke the USB debugging authorisations. Wireless debugging listens on a port of its own and stays open when USB debugging goes off (seen on a Chromecast with Google TV 4K). Note that port before you switch it off (adb mdns services lists it as _adb-tls-connect._tcp) and check it straight after, before the reboot: python3 tools/adb-closed.py <tv ip> <port> must say that port is closed. After the reboot the old number reads closed either way: Wireless debugging takes a new port each time it starts.
  2. Reboot the TV, then confirm the port is gone from your computer: python3 tools/adb-closed.py <tv ip> must say the port is closed. Wireless debugging must still be off in Developer options, and adb mdns services must list no _adb-tls-connect._tcp entry for the TV; if it came back, switch it off and check its new port as in step 1. With nc -vz <tv ip> 5555, only "Connection refused" counts: on macOS, Local Network privacy can block nc and make it fail with "No route to host" even while the port is open.

The launcher keeps working without debugging.

Can it block ads inside apps too?

Partly, with Android's Private DNS (Android 9 and newer). Point it at an ad-blocking resolver such as AdGuard DNS and every app's ad and tracker domains stop resolving, system-wide, surviving reboots. The trade-off: that resolver then sees every DNS query the TV makes.

tools/tv.py 'settings put global private_dns_specifier dns.adguard-dns.com'
tools/tv.py 'settings put global private_dns_mode hostname'

It does not remove YouTube ads, which come from the same servers as the videos. When the TV reports "No internet", the resolver is down or unreachable and switching back restores everything: tools/tv.py 'settings put global private_dns_mode opportunistic'. That line needs debugging back on, because Android TV's Settings app has no Private DNS page (not in AOSP, and not in Google TV 14 on a Chromecast with Google TV 4K); ADB goes to the TV's address, so it connects while the resolver is down. A resolver that answers can still break one app on its own, so if a single app fails while the rest play, see one app refuses to play before you debug the app.

Are there switches in the TV's own Settings worth flipping too?

A few. They need no ADB, the remote switches them back, and the debloat leaves them in place (Usage & diagnostics and Apps only mode aside): their pages belong to Settings and Play services, which every list keeps. The paths are Google TV's; other Android TV builds move some of them.

  • Settings → Privacy → Ads: delete the advertising ID, or turn on Opt out of Ads Personalization. On Android TV it is under About → Legal information → Ads (in Device Preferences on some sets).
  • Settings → Privacy → Location off. The launcher's network pill may then say "Wi-Fi" instead of the network's name.
  • Settings → Privacy → Usage & diagnostics off, before the debloat. On a Chromecast with Google TV 4K the page comes from setupwraith, which most Google TV lists disable for the launcher swap, and on a Hisense 50A6H4 it opened nothing after the debloat.
  • Settings → Network & Internet → Scanning always available off. It lets Google's location service and other apps scan for Wi-Fi networks even while Wi-Fi is off, so it matters most on a TV on Ethernet.
  • Settings → Accounts & Sign In → your profile → Apps only mode, where launcherx stays enabled (stock_home_redirect, or the Chromecast's debloat-keep-cast.txt). Google TV's own home then drops its personalised recommendations and casting still works, but Search and the Assistant switch off. The switch lives in launcherx, so a list that disables launcherx takes it away.

On Fire OS: Settings → Preferences → Privacy Settings, with Interest-based Ads, Device Usage Data and Collect App Usage Data off. They sync with the Amazon account, so change them in the menu, not with settings put.

AirPlay?

Not from this repo. Chromecast built-in stays for Android phones. For iPhones, jqssun/android-airplay-server works; an install script for it is in PR #84.

Can I just download the APK?

Build it with the one-line script; it takes a minute and you control what goes on your TV. No prebuilt binaries.
