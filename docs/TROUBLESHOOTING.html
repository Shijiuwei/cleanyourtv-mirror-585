Troubleshooting

Things that bit us or contributors, so they don't bite you. Commands use tools/tv.py; see the README for setting it up.

Connecting

  • macOS: "No route to host" (EHOSTUNREACH) although the port is open. Recent macOS keeps a process off the local subnet under Local Network privacy, and the kernel reports that as this error, the same one a TV that is switched off gives. tools/tv.py does not avoid it: the permission belongs to the app that runs the client (Terminal, iTerm2, VS Code), not to the adb binary or to python, so changing ADB client makes no difference. Allow that app under System Settings > Privacy & Security > Local Network, then quit and reopen it; a denial sticks once it has happened, and a prompt with no window to appear in is denied for you. Confirm it before changing anything on the network, with the default gateway: in practice it keeps answering while every other address on the subnet gives this error, so if the router connects and nothing else does, it is the permission and not the network. ARP and mDNS keep working throughout, which is what makes it read as AP isolation or a router firewall: arp -an shows the TV's MAC and dns-sd -B _androidtvremote2._tcp still finds it by name while no port on it can be opened. Seen on macOS 26 (Darwin 25.6) against a Hisense hengshan set, Google TV 12, where the stock adb and tools/tv.py failed identically.
  • No "wireless debugging" toggle on some TVs, Xiaomi among them. USB debugging alone opens network ADB on port 5555.
  • USB debugging is greyed out and there is no Wireless debugging entry either, seen on a carrier box (Airtel Xstream, Android 11). Some ISP firmware removes both switches, and then no shell can be reached: tools/tv.py fails, adb connect <ip>:5555 times out, and so does a port check. That timeout is the firmware, not Wi-Fi, the router or the cable, so don't go rebuilding the network for it. Greyed-out rather than missing points at a device-owner policy or a provisioning lock; the toggle comes back after a firmware update from the ISP, or not at all. Without one of the two switches this repo has nothing to talk to.
  • Developer options is hidden, or Build number asks for a password, seen on an ISP box (FPT Play 650, Android TV 14): tapping Build seven times opens a password prompt instead of unlocking the menu. Often only the way in is locked, not the screen itself: TvSettings still has com.android.tv.settings/.system.development.DevelopmentActivity, and any app can open it by its name or with the android.settings.APPLICATION_DEVELOPMENT_SETTINGS action. Install an app that opens activities by name (Activity Launcher) from the Play Store, open that screen and switch on USB debugging there. When no app can open it either, see the carrier-box bullet above.
  • USB debugging never opens port 5555 on some Google TV sets (a Skyworth-built Philips among them). Pair once through Wireless debugging with the stock adb (adb pair <ip>:<port> <code>, then adb connect), run adb tcpip 5555, and tools/tv.py works from then on. dns-sd -B _adb-tls-pairing._tcp (or adb mdns services) shows the pairing port while the code is on screen. Android switches Wireless debugging off whenever Wi-Fi drops; turn it back on and adb reconnects without a new code. Port 5555 from adb tcpip usually lasts only until the next reboot. When you close up, switch Wireless debugging off on its own: on a Chromecast with Google TV 4K (sabrina) turning USB debugging off left the Wireless debugging port accepting connections, and tools/adb-closed.py checks 5555 unless it is given that port. adb mdns services lists the port as _adb-tls-connect._tcp while it is open: note it before switching Wireless debugging off, and run tools/adb-closed.py <tv ip> <port> straight after, before the reboot. After the reboot the old number reads closed either way, because Wireless debugging takes a new port each time it starts.
  • Port 5555 stays closed and there is no Wireless debugging entry either, so the pair-once recipe above has nothing to pair with: a Philips 58PUS8505/62 The One, Android TV 12, STT2.230526.001 reported USB debugging on, no Wireless debugging screen, adb connect <tv ip>:5555 refused, and a USB cable to the computer that got no connection either. Two routes are left, and the firmware has to offer one of them. The first is the port-scan bullet further down this section: some firmware runs adbd on a port of its own, so scan and try each open one with TV_PORT=<port> tools/tv.py --probe. The second is the cable, when adb devices lists the set while USB debugging is on: adb tcpip 5555 with the stock adb then opens the port, the cable comes out, and tools/tv.py reaches the TV over the network. The cable is only a way to open the port, never a way to run these tools: tools/tv.py connects with AdbDeviceTcp(HOST, PORT) - <tv ip>:5555, or TV_PORT for another port - and carries no USB transport, so no script here talks to a TV over USB. A set that neither enumerates over USB nor runs adbd on any TCP port has no way in, and this repo does not try to get around that.
  • USB devices go dead while USB debugging is on, seen on the Xiaomi Mi Box S and the Xiaomi TV Box S 3rd gen (MiTV-AFMU0, Google TV 14): their firmware switches the USB port to ADB device mode, which cuts the power to a USB speaker or drive. A USB Ethernet adapter sits on that same port, so the network goes with it and the box falls back to Wi-Fi without saying so. dumpsys usb | grep host_connected prints false; dumpsys connectivity | grep -o 'Transports: [A-Z]*' prints WIFI on a set the owner calls wired. A bare eth0 stuck at NO-CARRIER is these boards' own socketless MAC, not the adapter - on the TCL 65C735 the adapter came up as eth1. How long the port survives debugging differs by firmware: the two Xiaomi boxes lose it as soon as debugging is on, while the 65C735 kept the adapter until a reboot with debugging still on put the port in gadget mode (sys.usb.config=adb, Mstar-udc) and it never came back (that list's header). Either way there is no way back from the shell on a set with no Wireless debugging, and switching USB debugging off stops adbd too, so plan one sitting rather than two: switch debugging off at the end, replug the adapter, and confirm Ethernet before handing the TV back. The launcher never needs debugging. A Chromecast with Google TV 4K (sabrina, UTTC.250917.004) kept its USB Ethernet adapter with USB debugging on: eth0 stayed listed, and Ethernet connected with debugging still on. It printed host_connected=false while the adapter was present as eth0, so there host_connected=false was no proof the adapter was gone (its list).
  • Port 5555 refuses the connection although network debugging is on, and no Wireless debugging is advertised, seen on a Wanbo T6R Max projector (MediaTek MT5862, Android 9, TVOS-04.16.031.01.12): the firmware starts adbd on its own port, 5877 there (service.adb.tcp.port), and the TV never shows it. Scan the TV's TCP ports (nmap -p- <tv ip>, or a short Python loop over socket.connect_ex; skip nc on macOS) and try each open port with TV_HOST=<tv ip> TV_PORT=<port> tools/tv.py --probe: the ADB one answers, the others time out. Every script here honours TV_PORT, and the closing check is tools/adb-closed.py <tv ip> <port>.
  • Close port 5555 when you're done: plaintext, and a shell for anyone on the LAN when ro.adb.secure=0. Steps in the README FAQ.
  • The TV sits on a separate VLAN or IoT network and tools/tv.py times out although debugging is on: the router keeps the computer from reaching it. Add a temporary firewall rule from your computer to the TV on tcp/5555 only, and remove it again when you close ADB. Opening the whole segment, or moving the TV onto the main network for good, undoes the reason it was separate.
  • Nothing on the network answers while a VPN runs on the computer, not even the router: ping prints General failure on Windows and port 5555 times out, although the TV is on the same Wi-Fi and arp -a lists it. Seen with Proton VPN's free plan on Windows 11, working on a Sankey SMART_TV (CVTE, HiSilicon Hi3751V350, Android 12). The VPN client's firewall blocks the local network; marking the Wi-Fi as a private network does not change that. Turn on the client's local-network option and reconnect: Windscribe has Allow LAN traffic (Preferences > Connection) on its free plan, Proton VPN's Allow LAN connections is for paid plans only. Or disconnect the VPN for the session. Turn the option off again afterwards if you use public Wi-Fi.
  • tools/tv.py times out after the TV took the connection (ADB did not finish the handshake, TcpTimeoutException: Reading from <tv ip>:5555 timed out) and no "Allow USB debugging?" prompt is waiting: another ADB client may be holding the TV, as some firmware's adbd serves one client at a time. Stop that client for the session, then run tools/tv.py --probe again. The stock adb server is one: if adb devices lists the TV, run adb kill-server first. A Xiaomi Mi TV 4A, Android 6.0.1 timed out whenever that server held a connection to the same port. Home Assistant's Android Debug Bridge integration is another (its Android TV Remote integration does not use ADB): a TCL 55C61B, Google TV 12 owner had to disable it in Home Assistant first, because it was holding the TV's ADB connection.
  • Windows PowerShell 5.1 adds a byte-order mark to text piped into a program, which turned the first batch command into gibberish. tv.py now strips it, and the .ps1 scripts pipe clean UTF-8.
  • "Allow USB debugging?" comes back, or the TV answers unauthorized although adb devices already works: tv.py keeps a key of its own in tools/adbkey/ and offers the stock ~/.android/adbkey (#105) after it, so a set that trusts either key connects with no prompt. Older copies offered the stock key only while tools/adbkey did not exist, which kept a TCL 55C61B unauthorized (#1526), so update the checkout first. When the TV trusts neither key, the prompt asks for tv.py's own. To have it register the stock key instead, so adb and tv.py share one approval, delete the folder: rm -rf tools/adbkey (Remove-Item -Recurse -Force tools\adbkey in PowerShell, rmdir /s /q tools\adbkey in Command Prompt), then tools/tv.py --probe (tools\venv\Scripts\python.exe -I tools\tv.py --probe on Windows) and accept that one prompt. Every attempt with an unaccepted key queues one more prompt on the TV, so dismiss them all (Back) before testing with key presses.
  • Git Bash rewrites paths like /data/local/tmp into Windows paths. The scripts set MSYS_NO_PATHCONV=1 for you. Set JAVA_HOME and ANDROID_HOME before building there.

Working on the TV

  • Chained pm commands (pm disable a; pm disable b) may silently stop after the first. Run one per shell call; --batch does exactly that.
  • TCL's software update says "Local network or server abnormal" after the debloat, while the network works. TCL's updater gets the TV's device number (dnum) from com.tcl.xian.StartandroidService, which the lists disable as reporting; without it the check stops with dnum is null! in logcat. Enable it, reboot once (it starts at boot), run Settings > About > Software Update > Network Update, then disable it again. Seen on a TCL Smart TV Pro (G03_4K_US, Google TV 11, GTV93).
  • The Google Home panel (lights) is gone from the quick settings on Google TV. It lives in com.google.android.apps.tv.dreamx, the same package as the promo screensaver, and Apps only mode hides it too. Re-enable dreamx and switch Apps only mode off to bring it back; the screensaver can stay on the launcher's clock. Seen on a TCL Smart TV Pro (G03_4K_US, Google TV 11, GTV93).
  • The Google Home panel opens and closes at once, though dreamx is still enabled, once the stock launcher is off: dreamx (com.google.android.apps.tv.dreamx) loads the panel's account and the device trust through launcherx, so with com.google.android.apps.tv.launcherx disabled logcat shows Failed to find provider info for com.google.android.apps.tv.launcherx.coreservices.account.AccountModeContentProvider, then EligibilityManagerImpl: SmartHome: Error loading account, and a bindService to launcherx's TrustedNetworkStateService returning false. Re-enabling launcherx brings the panel back straight away, with no reboot. Sparing launcherx's home activity alone is refused as well (Shell cannot change component state, as in the bullet on pm disable <package>/<class> below), so it is the whole package or the panel: if the household uses Google Home lights, keep launcherx enabled and hand Home to the new launcher with stock_home_redirect (themes/README.md) instead of disabling it. Seen on a TCL Smart TV Pro (G03_4K_US, Google TV 11, GTV93, #1653).
  • Large pushes hang through the Python client. Use tools/b64push.py for APKs.
  • tools/tv.py reboot never comes back. reboot is a shell command, and adbd stops before it sends the shell's last CLSE, so the client waits for a reply that cannot arrive: two minutes, then an error, on a TCL 65C935 (G05_4K_GB, Google TV 11, AR2101, #995). A chain that reboots and then checks something stalls there. Use tools/tv.py --reboot: it sends the reboot through ADB's own service and returns once the request is accepted. The TV is still restarting at that point, so let it answer again (tools/tv.py --probe) before the next command.
  • A logcat without the line you expected is not proof that nothing happened. On a TCL 55C728 (G05_4K_GB, Google TV 11) the main buffer is 1 MiB (persist.logd.size.main), and the TV's own HDMI, ARC and media logging fills it in well under a minute; around power-on it held about 30 seconds. A wake or boot event read a minute later is already gone. Enlarge the buffer for the session with tools/tv.py 'logcat -G 16M' (logcat -g shows the size; a reboot brings back the firmware's), or keep logcat running from before the event. For sound, dumpsys audio keeps a history of player events that outlasts the log.
  • Every way of disabling a package is refused, not just one. On a Fire TV Box 2015 (sloane, Fire OS 5 / Android 5.1) pm disable-user --user 0 returns SecurityException, pm uninstall --user 0 returns DELETE_FAILED_INTERNAL_ERROR, and pm hide reports success while pm list packages -d stays empty (#577). Read pm list packages -d after each attempt instead of the exit code - pm hide is the one that lies. When all three refuse, this firmware does not take a debloat list at all: there is no shell route around it, sponsored rows stay on the home screen, and the only useful work left is the TV's own privacy toggles plus DNS blocking (Pi-hole with a smart-TV ad list; the report used Perflyst's AmazonFireTV list). Fire OS 6 is the opposite case: pm disable-user works and about ten Amazon packages are protected, which examples/amazon-fire-tv-stick-4k-2018/debloat.txt lists, with the same DNS fallback for their endpoints.
  • pm disable <package>/<class> is refused with Shell cannot change component state, the SecurityException you get when you try to keep a package and switch off only its Home activity or boot receiver. The notes here have it for setupwraith's .RecoveryActivity (TCL G08, Chromecast with Google TV HD, Google TV Streamer), launcherx's .home.HomeActivity (XGIMI MoGo 4), boot receivers on a Fire TV Stick Lite (Fire OS 7) and a Motorola MT4310 (Android TV 11), and the ERGO DVB92YC's Live TV boot receiver below. It is not that firmware: from Android 7.0, AOSP's PackageManagerService lets the shell change only a whole package, and only between default, enabled and disabled-user (from 8.0 a test-only APK is the exception). The same check refuses pm disable and pm disable-until-used on a whole package, which ask for other states, and any change, pm enable included, to a package that is already disabled (enabled=2 in dumpsys package, as tvrecommendations is on a Chromecast with Google TV 4K). There is no shell route around it, so don't retry it with other flags: disable the whole package with pm disable-user --user 0, or keep it.
  • pm disable-user answers Error: java.lang.IllegalArgumentException: Unknown package: <package>, by hand or for one line of a list (#1880, a Konka B50U). Nothing of that name is installed for the user the command names, so that one line changed nothing - and the lines around it still run: tools/disable.sh pipes the list into tools/tv.py --batch, which runs each line as its own shell call and carries on to the next whatever this one answered, so a list with three unknown names in it still finishes, and the client's exit status says nothing about them. What the line is worth is the name in it. Two causes. The list was written on another set: every list here names the model and firmware build in its header, preloads differ between regional builds of the same model, and examples/tcl-c845x2-google-tv/debloat.txt calls its own two Unknown package errors harmless for exactly that reason. Or the name is not a package at all: a store title, a home-screen tile, or a name guessed from the app's look, as com.vendor.recommendations was. pm list packages is the only list of names the TV answers to, and a fragment of the app's name usually finds it: 
    tools/tv.py 'pm list packages | grep -i recommend'
tools/tv.py 'pm list packages -u --user 0 <package>'    # -u: one removed earlier still shows
    Nothing from the first command means the app is not on this TV, so comment its line out of the list instead of retrying it - and check the model and Android version tools/tv.py --probe prints against the header of the list you are following. A name the TV does list is the case the bullet below covers: tools/recovery.py records a listed package that was already gone before the first run as absent, and restore.sh and check.py say so in their own words.
  • A package removed with pm uninstall --user 0, by hand or by another debloat tool, stays gone after tools/restore.sh. The Toshiba 55Z500QF note (Hisense firmware, Android 11, RD2A.211001.002) has 23 preinstalled packages its owner removed that way. The command takes a package away from user 0 only, and a preinstalled one keeps its APK on the system partition. pm list packages -u --user 0 <package> still names it (-u adds uninstalled packages) and the same command without -u does not; the User 0: line of dumpsys package <package> says installed=false. tools/recovery.py records a listed package that is already gone when tools/disable.sh first runs as absent, so restore.sh prints leaving <package> alone (absent when the record was taken), and tools/check.py lists it under "not installed any more". Bring it back with tools/tv.py 'cmd package install-existing --user 0 <package>' (AOSP's cmd package has it from Android 8.0; the Android 6 set in #1185 had no such command; no TV here has run it yet). It comes back without its data unless the uninstall used -k, and disabled if a list that names it has gone through disable.sh since it was removed: that run sent it pm disable-user --user 0, which AOSP applies to a package removed for user 0 too (the Shield list notes disable.sh reporting "disabled-user" for such packages), and install-existing marks it installed without changing that state. pm list packages -d --user 0 <package> names it if it came back disabled. To keep it, comment its line out of your list, then run tools/tv.py 'pm enable --user 0 <package>': with the line still in, check.py reports it as back on, and --fix or the next disable.sh run disables it again. If you don't want it, keep the line: the list disables it, or keeps it disabled, which the TV's own settings can undo. --fix or a disable.sh run that finds it enabled first changes it from absent to enabled in the record, so restore.sh turns it back on too. Until then, or in a record an older version updated, it stays absent, and restore.sh leaves it alone: pm enable --user 0 <package> is its undo. Two cases this does not cover. An app with no copy on the system partition that only user 0 had is deleted with its APK: the command answers Package <package> doesn't exist, and only reinstalling the APK brings it back (the Toshiba's com.hisense.business.ad). And a User 0: line with installed=true hidden=true was hidden, not uninstalled. install-existing changes nothing there even though it prints Package <package> installed for user: 0, and the shell cannot unhide it: pm unhide needs MANAGE_USERS, which the shell does not hold from Android 7.0. Unhide it from the device-owner app that hid it, or leave it, as the Chromecast with Google TV 4K list does with cast2class (hidden=true and enabled=2 there).
  • The Input key and CEC die after the hidden factory menu is opened, seen on a Haier/CVTE set (Durabrand DURAT32ISDB, dupont, Android TV 11 build RTM6.230109.232, #470). com.cvte.tv.hkcfac is the manufacturer's production app: dumpsys package shows it as a factory component, and it has a launchable activity, so "let me see what this package does" is enough to trigger it. Opening it sets customer_factory_mode=true in /vendor/tvcertificate/fdata.ini and vendor.mtk.factory.disable.input=1. The Input button then does nothing and HDMI-CEC is off, and at the next boot com.at.factory.factorymanager disables Play services, Netflix, com.google.android.katniss and com.google.android.apps.mediashell - pm enable from the shell is refused for those, so casting and the store stay gone until the mode is cleared. Read the package instead of starting it. If it has already been opened, start it, send the factory-exit keycode twice with it in front, reboot, then turn CEC back on: 
    tools/tv.py 'am start -n com.cvte.tv.hkcfac/.MainActivity'
tools/tv.py 'input keyevent 218; input keyevent 218'
tools/tv.py --reboot             # returns once ADB accepts it; wait for the TV to come back
tools/tv.py 'settings put global hdmi_control_enabled 1'
    Press the real Input button afterwards and check the packages are back: tools/tv.py 'pm list packages -e | grep -E "gms|netflix|mediashell|katniss"'. More on the unit in the device notes.
  • Stremio looks like its server died after the debloat, seen on a Xiaomi MiTV-MZTU0 (river, Google TV 14, list). The app opens, the add-ons load, and nothing ever plays, which reads like a local server fault. It is not: with com.google.android.apps.mediashell disabled, Stremio's own stremio_server_process is still running, still listening on 11470/12470, still holds ESTABLISHED connections to api.strem.io, and logcat -b crash is clean. Stremio's Android TV build plays through mediashell, so the server is healthy and the playback path is gone. pm enable --user 0 com.google.android.apps.mediashell fixed it on that set with no reboot and no reinstall. Check this before blaming your add-ons or the network: 
    tools/tv.py 'pm list packages -d | grep mediashell'     # output here = this is the cause
tools/tv.py 'pm enable --user 0 com.google.android.apps.mediashell'
    Keep the package out of your list if you use Stremio on the TV, or cast from a phone.
  • Picking HDMI 1 in the Inputs menu opened an unrelated app, seen on an RCA Android TV 9 (Toptech/Zeasn firmware RTK2851P, Realtek RTD2851P, #805). The launcher switches to a passthrough input with an implicit ACTION_VIEW on the input's channel URI (vnd.android.cursor.item/channel), and only sends the theme's input_action when nothing claims that intent at all. "Nothing claims it" is the catch: that firmware has no Live TV app for the URI, and ES File Explorer (com.estrongs.android.pop/.app.transferstation.FileTransferStationActivity) declares a VIEW filter for the same MIME type, so HDMI 1 opened the file manager and input_action was never reached. A set with no handler at least shows "Not available on this TV"; a set with one wrong handler opens that app. Ask which app would take a row before blaming the launcher: 
    tools/tv.py 'cmd package query-activities --brief -a android.intent.action.VIEW -t vnd.android.cursor.item/channel'
    live_tv_package does not help: it is applied as setPackage on the Live TV row only, and the HDMI and AV rows carry no package. Until the launcher checks that the handler is a TV-input app, hide the rows instead: a theme with source_panel_service set and live_tv_package empty makes the Inputs pill open the TV's own source panel (what the reporter did), or disable the app that answers when it is not a Live TV or input app. tools/disable.sh (disable.ps1) keeps any listed app that query names and skips it with "the TV opens its HDMI/AV inputs and channels with it", so put its line in a list of its own and apply that with HANDLERS_ALLOW=1 ($env:HANDLERS_ALLOW): the rest of your list keeps the guard. Run tools/venv/bin/python -I tools/check.py --fix on that list with the same switch, or it leaves the app on and exits 1. disable.ps1 reads the switch once and clears it from the environment, so one $env:HANDLERS_ALLOW=1 covers only that one run (#1845); check.py --fix still reads it, and in PowerShell it stays set until the window is closed: run Remove-Item Env:HANDLERS_ALLOW after those two, or a later check.py --fix on your main list skips the guard too. To turn the app back on, use tools/tv.py 'pm enable --user 0 <package>'. tools/restore.sh with that list turns it back on as well, but it also turns the stock launcher back on and makes it Home, as it does for any list. Report another one rather than reading it as a firmware quirk: the wrong-handler case needs a source change, not a setting.
  • adb exec-out screencap -p gives a broken PNG on some MediaTek sets (Xiaomi, and Amazon's own Fire TV smart TVs): the binary prints Init wrapper sys mutex successful on stdout first. Save on the TV and pull the file instead: screencap -p /data/local/tmp/s.png, or cut everything before the \x89PNG header. tools/tv.py --screenshot shots/home.png does the save, the pull and the cleanup in one command, and says so when the capture is 0 bytes.
  • Gradle says "Your project path contains non-ASCII characters" on Windows before building the launcher. Android's build tools reject a checkout under a localized folder such as 桌面 (Desktop). This was seen while installing on a Sony KM-55X85J (Google TV 12, Taiwan firmware); the TV is not changed when the build stops here (#1777). Clone the repo into an ASCII-only path such as C:\cleanyourtv, or map a drive letter to the checkout's parent directory and run the build through it: 
    subst X: 'C:\Users\<user>\OneDrive\桌面\sideproject'
Set-Location X:\cleanyourtv
powershell -ExecutionPolicy Bypass -File launcher\build-and-install.ps1 -TvHost <tv ip>
Set-Location C:\
subst X: /D  # after the build is finished
  • Play Protect blocked the launcher ("unsafe app blocked, built for an older version of Android") and pm install hung, then failed with INSTALL_FAILED_VERIFICATION_FAILURE, while it targeted SDK 29. It targets 34 now; if you built an old checkout, rebuild.
  • pm install fails with INSTALL_FAILED_OLDER_SDK on a set older than the launcher: the APK's minSdk is a compile-time floor, so a TV on Android 7.0/7.1 (SDK 24/25) cannot take the published build at all (#576). Read both numbers before changing anything: tools/tv.py 'getprop ro.build.version.sdk' and grep minSdk launcher/app/build.gradle (26, i.e. Android 8.0, at the time of writing). launcher/build-and-install.sh now asks the TV first and stops with both numbers, so nothing is built or pushed for a set that will refuse it; build-and-install.ps1 only reports it after pm install, which fails safely with the stock launcher untouched. Lowering minSdk is a source change, not a setting, and it means maintaining your own copy: the launcher uses AndroidX and framework calls newer than API 25, so expect compile errors or a launcher that starts and then crashes. An APK produced by rebuilding the project elsewhere (an assistant, an online builder, a "rebuilt for API 25" zip from a forum) is not something this repository can check, and the install scripts only push the APK they compiled themselves: a build signed with another key does not install over this one (INSTALL_FAILED_UPDATE_INCOMPATIBLE), so uninstall the old one first if you go that way, and keep the stock launcher enabled until the new one really starts. On a set below minSdk the debloat and privacy half still applies, from the TV's own home screen: it is the launcher that cannot be installed, not the lists. If the Failure [...] line names INSTALL_FAILED_VERIFICATION_FAILURE instead, that is the bullet above - the firmware's installer verifier, not the API level.
  • Screenshots come out empty while Live TV, an HDMI input or Netflix is on screen, seen on TCL and a Sony KDL-49W800G. Press Home before screencap. An empty capture means nothing about the ADB connection or playback; check those separately.
  • Screenshots come out identical instead of empty, seen on an Amazon Fire TV Stick 4K 2nd gen (AFTKRT, karat, Fire OS 8) right after a reboot: screencap -p kept returning the same non-empty PNG byte-for-byte (same MD5) across completely different resumed activities, minutes apart. It looked like a real (black) capture and cost real debugging time before md5-comparing two pulls gave it away. dumpsys SurfaceFlinger --display-id showed no identification data for Display 0 at the time. Don't trust a screencap pull on its own here: diff it against another pull, or check dumpsys activity activities | grep mResumedActivity and real key events (adb shell getevent -lt) instead.
  • The whole UI is huge and clipped, and it is not the launcher, seen on a Sony K-85XR70 (BRAVIA 4K AE2, Android 14, China firmware, #590). Its UI runs at 1920×1080 on a 4K panel by design (#29), and two confirmed boots came up with an override density of 640 where 320 worked: everything doubles in size, tiles clip, and it looks like a grid bug. Read the overrides before touching the layout: 
    tools/tv.py 'wm size'          # Physical size vs Override size

Remapping the remote's app buttons without a key helper

A process of your own can take the buttons the helpers exist for without binding an accessibility service, and the key auto-repeat a helper costs stays: a key-filtering service pushes every key through a filter path that drops the repeats, while reading the remote's input device leaves Android's input alone. It has to run as the shell user, because a normal app cannot open /dev/input/event*, so this is not something the launcher can grow into — it is a script and a supervisor on the TV. On a Google TV Streamer (kirkwood, Google TV 14, UTTK.260317.003) that was the one way to have both: HomeKeyService alone, InputKeyService alone and both together each stopped the ramp after roughly six steps, and it came back the moment the service was unbound (#796).

The Streamer's remote appears as Google TV Remote Keyboard, and these are the buttons it sends:

ButtonHID usageAndroid keycode
YouTube0x000c0077BUTTON_3 (190)

Netflix0x000c0078BUTTON_4

Find the node by name, not by number: tools/tv.py 'getevent -pl' lists every input device with its name and the key codes it declares, and the /dev/input/event<N> a remote lands on is not stable between boots, so a watcher pinned to event5 stops working after the next reboot and reads as a dead button again.

A reader cannot consume the press. getevent observes the events and Android still delivers them to whatever answers them today, so a remapped button's stock action runs as well: map the Netflix button and Netflix starts too, then sits in the activity back stack. A helper consumes the key it maps — which is why the vendor receiver in the "Which keycode" bullet above never sees it — so the buttons you have to suppress, rather than duplicate, still need a helper and its repeat trade.

What runs it again after a reboot is the part that is not free. The shell user reads /dev/input/eventX on this unit without root and a script kept under /data/local/tmp/ runs, but nothing there starts itself: Android gives the shell user no cron and no init hook without root, so the watcher is gone after every reboot and has to be started again from a debugging session you close afterwards. Two things fail silently when you do: the script must be detached from the adb shell session or it dies with it, and a supervisor must not start a second copy. Do not solve the reboot by leaving TCP ADB on so something local can restart it — port 5555 reachable from the LAN is a shell on the TV for anything on the network, which is why the closing step in README turns it off.

tools/tv.py 'settings get secure enabled_accessibility_services'
tools/tv.py 'settings get secure accessibility_enabled'
tools/tv.py 'dumpsys accessibility'

Where launcherx is what answers the buttons, keeping it enabled and redirecting its home screen keeps both. On a Sony BRAVIA VU3 (BRAVIA_VU3_4K, Google TV 14, UKR1.240726.001) the Netflix, YouTube, Prime Video and YouTube Music buttons are global keys (BUTTON_4, BUTTON_14, BUTTON_2, BUTTON_15) routed to com.realtek.advancesetting, which on a Google TV hands each launch to launcherx's GlobalButtonLaunch_Receiver and drops it when launcherx is disabled. It is not a stock upstream option.

The power key does not wake the TV while the key helper is bound

A remote's power button does nothing while the TV is in standby, and only the set's own button wakes it. Seen on a TCL tc8000_ay30a2 (Android 11, RQ3A.210705.001.2024101221, #1387), where a key-filtering accessibility service that stays bound with the screen off was reported to swallow the power key. The launcher can stand its own helper down for standby instead of losing the helper altogether: with HOME_KEY_SERVICE=1 at install, at screen-off HomeKeyService takes itself off the accessibility list and the first screen-on puts it back, so the keys it answers still work whenever the screen is on. Off by default; three writes turn it on, and none of them is part of an ordinary install:

tools/tv.py 'pm grant com.gathin.tvhome android.permission.WRITE_SECURE_SETTINGS'
tools/tv.py 'cmd notification allow_listener com.gathin.tvhome/.GuardRevival'
tools/tv.py 'am broadcast -a com.gathin.tvhome.GUARD -n com.gathin.tvhome/.GuardConfig --ez guard_off_in_standby true'
# off again:
tools/tv.py 'am broadcast -a com.gathin.tvhome.GUARD -n com.gathin.tvhome/.GuardConfig --ez guard_off_in_standby false'

The broadcast prints guard_off_in_standby=true back, so the answer is readable without a reboot. The first two writes are what make the opt-in survive, so read why:

  • WRITE_SECURE_SETTINGS is what lets the launcher write the helper back onto the list at screen-on. Without it GuardKeep gives up silently and the helper stays off after the first standby, which looks like the helper having died. RESTORE_KEY_SERVICES=1 at install already grants it (the force-stop section).
  • GuardRevival is the listener the system re-binds once the process is gone, and firmware that kills third-party apps in standby takes the screen-on watch with it. The rebind is what re-arms it.

While the opt-in is on, dumpsys accessibility naming no com.gathin.tvhome/.HomeKeyService during standby is the opt-in working, not a fault: wake the TV and read it again. Only that helper stands down; InputKeyService keeps filtering, so the Input button still works.

A power button that does nothing at all while the TV is on, with a long press opening the shutdown dialog instead, is a different fault: a TCL 43BP615 whose stock launcher switched the TV off on one press.

A power press that does nothing and a long press opens the shutdown dialog

A press on the remote's power button does nothing, and a long press brings up Android's shutdown confirmation instead of turning the set off, where the stock launcher switched it off on one press. Checked on a TCL 43BP615 (BeyondTV, Android 11, SDK 30, #1608) after an ordinary launcher/build-and-install.sh with no key helper flags, and again with HomeKeyService bound through settings put secure enabled_accessibility_services: the dialog came up both times, so the helper is not what changes the key. The owner's reading is that the platform takes KEYCODE_POWER itself, in the window policy, before an application or an accessibility service is handed it, and the launcher maps no power key of its own (its only KEYCODE_POWER mention keeps the key out of the power_on_home handover) — so there is no app_keys entry, theme key or config.xml value that takes the press back. On this set the one-press power-off belonged to the firmware's own home screen and went with it.

Nothing is broken: the install, the debloat and the key helper are not involved, and the shutdown dialog is Android's, so the TV still turns off from it. An owner who wants the one-press power-off back gets it by putting the stock launcher back — tools/restore.sh <list> <stock launcher> — and hands Home back to it at the same time.

The soundbar on ARC/eARC falls asleep and the TV does not wake it

A soundbar on the TV's ARC or eARC port can go to standby on its own after a stretch of silence while the TV stays on, and starting an app or a video does not bring it back until someone wakes it by hand. Seen on a Sony BRAVIA 4K VH2 (KD-55X80J, Google TV 12, STT2.230505.001.S136) with a Moto 160SB on HDMI 3 (eARC), with the TV's own settings already right (Speakers: Audio system, Audio system prioritisation on, BRAVIA Sync on).

The TV reports the state over ADB. While the soundbar sleeps, both values are false:

tools/tv.py 'dumpsys hdmi_control | grep -E "mSystemAudioActivated|mArcEstablished"'

Asking for System Audio Mode over HDMI-CEC wakes it, the same request the TV's Speakers → Audio system setting sends; the soundbar reconnects about 5 to 8 seconds later:

tools/tv.py 'cmd hdmi_control setsam on'

To have that happen without a computer, an app needs the shell: on Android 12 an app cannot send CEC itself, and writing the TV's speaker setting needs the maker's own permissions. These were tried on the VH2 and do nothing from an app: Android's system-audio setting, volume nudges, and Sony's audio service. What does work is an app that keeps Network debugging on and connects to the TV's own ADB on 127.0.0.1:5555 with its own key, which the TV asks to allow once, and runs only that one command when an app opens or media starts while no TYPE_HDMI_ARC/TYPE_HDMI_EARC output is listed. The Sony BRAVIA Launcher in SHOWCASE.md does this (SoundbarWaker.java). It is a trade-off: Network debugging stays on and the port is open on the home network, which the PROMPT's last step closes on purpose; on a set with ro.adb.secure=0 an open port is a shell for anyone on the network, so only consider it where the TV asks to allow each new key. On Sony, an app can instead open the Home Theatre Control panel (com.sony.dtv.HomeTheatreControl) for about half a second, which also wakes the soundbar and needs no ADB, at the cost of the panel flashing on screen.

Moonlight: two controllers both drive player 1, or a DualSense button opens the exit prompt

With HomeKeyService bound (HOME_KEY_SERVICE=1) and filtering keys, Moonlight streaming from Sunshine on a TCL G07 (G07_4K_GB_NF, Android 11, AR17) with a DualSense (054c:0ce6) and an Xbox Wireless Controller (045e:0b20), both over Bluetooth, put both controllers on player 1, and Cross on the DualSense brought up Moonlight's exit prompt instead of pressing A. Both controllers were listed in dumpsys input as separate devices with sources 0x01000511, so pairing was not the problem.

The DualSense half has a known shape: Android 11 ships no key layout for it, so dumpsys input shows KeyLayoutFile: /system/usr/keylayout/Generic.kl, and getevent -lp shows the generic HID order (BTN_GAMEPAD, BTN_EAST, BTN_C, BTN_NORTH, ...). Cross is BTN_EAST, which Generic.kl maps to BUTTON_B, and an unhandled BUTTON_B falls back to Back. Moonlight has a scan-code remap for this layout (isNonStandardDualShock4 in its ControllerHandler), but it did not take effect while the helper filtered keys, consistent with what GamepadPassthrough (#1118) describes: re-injected keys no longer read as the controller's own, so Moonlight could neither remap them nor tell the two controllers apart.

gamepad_passthrough fixed both: Cross acts as A and the second controller joins as player 2. Set it in config.xml and rebuild, or "gamepad_passthrough": true in a theme's config.json. The trade is the one in the key-repeat section above: the remote buttons the helper answers (gear, app buttons) do nothing while a controller is connected, and come back when it disconnects. To check what a controller reports:

tools/tv.py 'dumpsys input' | grep -E 'Controller|KeyLayoutFile|Sources'
tools/tv.py 'getevent -lp'

One app refuses to play while the rest of the TV is online

An ad-blocking Private DNS is a common addition and the resolver answering is not proof that playback is unaffected. A player also calls measurement and analytics domains, and a block there comes back as the app's own error while the TV stays online. On a Master-G MGA3200 (ATV R1, R1, SCBC, Realtek, Android TV 9, PTT1.201001.001) with dns.adguard-dns.com in hostname mode, Max (com.wbd.stream) logged ERR_CONNECTION_REFUSED for its Braze and Conviva endpoints and stalled, while every other app played and Android's own connectivity check passed (#1060). Blocking pixel.spotify.com takes Spotify off the Freebox Player POP (examples/freebox-player-pop) the same way. So when one app fails and the rest play, set the mode back before debugging the app, then try the same title once more - on the MGA3200 that cleared the errors:

tools/tv.py 'settings put global private_dns_mode opportunistic'

The other failure mode reads differently: when the TV itself says "No internet", the resolver is down or unreachable, and the same command restores it. What the optional resolver does, and what it costs, is in the README's "Can it block ads inside apps too?".

When you report how an app does on your TV, say how far it got, because each step can fail on its own: installed, opened, usable with the physical remote, signed in, and played a title with sound. Reaching the login screen is not playback. Quote the app's full error code (Netflix's UI-800-3, for example) rather than "doesn't work", since that is what the app's own help pages look up (#1008).

Xiaomi CN firmware: Settings freezes or crashes after the debloat

On China-market Xiaomi firmware the settings app is Xiaomi's own (com.xiaomi.mitv.settings), and it reads the TV's hardware configuration from the TvService system service that mitv.service registers. Disable that package and Settings breaks while everything else on the TV keeps working: opening it freezes for 20-30 s and drops back to Home (an ANR, not a reboot), and pressing Down twice from the first page, Network -> Display -> Sound, crashes it outright. Seen on a MiTV-ASTP0 (mulan, Android 9, SDK 28, Amlogic/droidlogic, 1.5 GB RAM; the version string says HyperOS 2, the base is still Android 9) in issue #1310, whose report could not quote ro.build.display.id: that firmware closes network ADB on every reboot.

The crash log names the cause:

tools/tv.py "logcat -b events -d | grep am_crash"
# java.lang.NumberFormatException, For input string: "NULL"   <- SoundView.init, Integer.valueOf

SoundView.init parses a value it got from mitv.common.ConfigurationManager with no guard, and with the service gone that manager retries ten times half a second apart, gives up and hands back the literal string NULL:

ConfigurationManager: getService() 0..9, service = null
ConfigurationManagerDefaultImpl: service null return

So it is neither the Settings app nor the debloat in general. mitv.service is /system/app/TvService, a PERSISTENT app whose TvApplication.onCreate starts TvServer, the thing that registers the service:

tools/tv.py "service list | grep -i tvservice"   # TvService: [mitv.internal.ITvService]

Keep the package. Every settings page that reads a hardware value then stalls about 5 s, and the one page that parses the answer crashes. The China-market lists here already say not to touch it; this is why.

Re-enabling the package on its own does not bring Settings back. The service is registered at boot and the disabled package's PERSISTENT process starts anyway, so nothing looks different after pm enable and it is easy to conclude the debloat was innocent - the reporter lost a day to exactly that. Start the service by hand instead:

tools/tv.py "pm enable mitv.service"
tools/tv.py "am startservice -n mitv.service/.TvServer"
tools/tv.py "service list | grep -i tvservice"      # expect: TvService: [mitv.internal.ITvService]

A restart registers it too, and on that firmware the restart also turns network ADB off while the switch that turns it back on sits inside the Settings app that is broken: have ADB open before the reboot, or count on reaching Settings by hand. examples/xiaomi-mitv-aesp0 is the one list here that disables the package (its second set, in daily use since 21 Oct 2026); carrying that line to a set whose settings app is Xiaomi's takes Settings with it.

Settings freezes, then closes, in Accessibility

The highlight passes over Accessibility > Text-to-speech output and Settings stops responding; a few seconds later Android closes it ("Input dispatching timed out"). TV Settings previews the focused row, and that row's page starts Google's speech engine (com.google.android.tts, "Speech Recognition & Synthesis" in the Play Store) to name the current voice. On a Hisense 75U75N (hengshan, Google TV 12, STT2.230310.002, 23 and 24 October 2026) the engine took more than ten seconds to start, and leaving the row before it answered left Settings waiting for it. The debloat does not touch the engine. The ANR report names the wait:

tools/tv.py 'dumpsys dropbox --print system_app_anr' | grep -m2 TextToSpeech
#   at android.speech.tts.TextToSpeech.shutdown(TextToSpeech.java:914)
#   at com.android.tv.settings.system.TextToSpeechFragment.onDestroy(TextToSpeechFragment.java:218)

Clearing the engine's data fixed it on that set; the engine downloads its voice again the first time it is used:

The router's domain rules stop applying to the TV after Private DNS

Private DNS in hostname mode sends every lookup over DNS-over-TLS straight to the resolver, past the router's own DNS. A router that filters or routes traffic by domain through its resolver - podkop and its forks on OpenWrt, mihomo/Clash in fake-IP mode, a VPN subscription with domain lists, Pi-hole or AdGuard Home - then never sees the TV's lookups, and its rules stop applying to the TV without any error. On a TCL Smart TV Pro (G05, Android 11, AR2101/AR28) behind such a router, with dns.adguard-dns.com in hostname mode, the TV got real addresses instead of the router's fake-IP range (198.18.0.0/15), so traffic the router would have sent through its tunnel went out directly: services that only work through that route broke or slowed down, and the resolver itself answered 127.0.0.1 for api.themoviedb.org (#1385).

To tell, compare the address the TV gets with the router's answer for the same host:

tools/tv.py 'ping -c1 -W1 <host>'     # the first line shows the address the TV resolved
nslookup <host> <router ip>           # on the computer: what the router answers

A fake-IP or other router-made answer next to a real address on the TV means Private DNS is going around the router. Then either set the mode back, so the TV asks the router again, and block ads on the router instead (most of these setups can):

tools/tv.py 'settings put global private_dns_mode opportunistic'

or keep Private DNS and accept that the router's domain rules no longer cover the TV. Write down which one you chose, so the next "this one service is slow on the TV" does not start from scratch.
